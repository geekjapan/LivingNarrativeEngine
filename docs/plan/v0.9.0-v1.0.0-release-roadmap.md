## 現在地

v0.8.0までに、長編Bookのdurable production、cross-book admission、reader-safe artifact index、100章provider非呼出benchmark SLO、operations metricsをmainへ統合した。ADR-0005/0010/0011が定めた既存のP0、mock 100ターン、UX、clean-install、migration regressionの実装Issueは完了している。

## v0.9.0: RC evidence hardening

### 目的

v0.9.0は、新しい生成品質の自動合格を偽装しない。実LLM実行と人手読解を置換せず、両者が提出するartifactを固定schema・revision・privacy規約に対して検証できるようにする。これにより、v1.0の判断材料を「手順書の読み合わせ」から「reader-safeな検証結果 + 人間判断」へ限定する。

### 作業分解

| ID | 検証可能なoutcome | 公開seam | 依存 | 完了条件 |
|---|---|---|---|---|
| 133 | 実LLM benchmark JSONとhuman rubric Markdownを、schema・30ターン完走・revision・禁止情報の規約に対して検証できる。 | `validate_real_llm_benchmark_artifact(path, expected_revision) -> RealLLMBenchmarkValidation` | ADR-0010、Issue 072、Issue 089 | 有効な30ターンartifactはpassし、途中停止・revision不一致・provider failure・禁止情報はfail。validatorはartifactを変更しない。 |
| 134 | validator結果をrelease checklistへ転記できるreader-safe summaryとしてCLI出力する。 | `living-narrative release verify-real-llm-evidence` | 133 | JSON / human-readable outputにprompt、credential、GM/private context、absolute path、本文全文を含めず、exit statusがrelease判定に利用できる。 |
| 135 | release candidateの自動確認をIssue 088 checklistへ対応付け、未達の人手gateを明示する。 | `docs/release-checklist.md`とRC evidence record | 133, 134 | 自動passと人手必須項目を混同せず、artifact path/hash・git revision・判定日時を記録できる。 |

### v0.9.0 出荷gate

1. Artifact validatorはreader-safe inputしか出力せず、Book State・run artifact・rubricを更新しない。
2. 有効・無効・privacy violation・revision mismatchについてTDD回帰を持つ。
3. mock 100ターン、Book 100章benchmark、existing release CIを含む全testがgreenである。
4. CLIを追加する場合、exit statusとJSON outputをCI利用可能な安定契約としてテストする。
5. v0.9.0の実LLM実行は**任意の定点観測**であり、credential・gateway未設定を隠蔽して成功扱いにしない。

## v1.0.0: formal release closeout

### ADR-0005 gate対応表

| ADR-0005の要件 | 既存実装・証跡 | v1.0で実施すること | 判定者 |
|---|---|---|---|
| α: mock representative journey | Issue 063、CI | release候補HEADでCI greenを確認 | 自動CI |
| β: uv/Docker clean install、βschema | ADR-0011、clean-install acceptance、`beta-schema-v1` | CI run URLをchecklistへ記入 | 自動CI + release担当 |
| β: 実LLM人手smoke | Issue 072/073、既存PASS artifact | Issue 089のgateway/keyを準備し、release候補HEADで30ターンを再実行 | 人間 + 実LLM |
| 1.0: quality gate | ADR-0010、Issue 070–073 | machine SLOとR1–R8をartifact verifierで確認後、人手rubricを署名記録 | 人間 + verifier |
| 1.0: UX受入 | Issue 076 checklist | clean新規/既存復旧の2セッションを実施し、evidenceを保存 | 人間 |
| 1.0: migration | βschema fixture / acceptance CI | release候補のmigration regressionを確認 | 自動CI |
| 1.0: release engineering | ADR-0011、Issue 088 | pip-audit、CHANGELOG、version 1.0.0、wheel/sdist/Docker、tag、GitHub Release | release担当 |

### 実行順序

1. **RCを固定する**。mainから`release/1.0.0-rc.N`を作り、v0.9.0 evidence hardeningをsquash mergeする。
2. **自動gateを実行する**。pytest、ruff、CI matrix、clean-install acceptance、migration regression、v0.9 artifact verifierを実行し、release checklistにURL/hashを記入する。
3. **実LLM gateを実行する**。Issue 089の人間操作でWSL gatewayとkeyを準備する。30ターンを15+15の別プロセスで実行し、provider failure・fallback・turn欠落があれば即FAILとする。
4. **品質とUXを人手で判定する**。実LLM runをR1–R8 rubricで判定し、UX Session 1/2を別記録として保存する。いずれも1件でもNOなら、原因をIssue化してRCへ戻る。
5. **出荷操作を行う**。`pip-audit`、CHANGELOG更新、version bump、wheel/sdist、tagged Dockerfile local build、annotated `v1.0.0` tag、GitHub Release添付の順に実施する。PyPI/registry pushは行わない。

## 非交渉契約

v0.9.0/v1.0.0の全作業で、Book Stateの変更はStateDiffのみを用いる。実LLM evidence・benchmark report・operations output・release summaryには、prompt、credential、GM/private context、absolute path、worker identity、traceback、本文全文を保存しない。人間のaccept/reviseを自動化せず、実LLM gateのpassを著者承認の代替にしない。

## 明示的な非対象

Web export/backup/init、review edit/rerunのWeb化、plugin sandbox/network isolation、PyPI publish、Windows native POSIX transaction対応、画像/TTS、実LLMの常時CI実行はpost-1.0とする。実LLM provider profile別のdelivery-latency alertは、v0.8.0のreader-safe aggregateに十分な実測baselineが蓄積されてから別Issueで導入する。
